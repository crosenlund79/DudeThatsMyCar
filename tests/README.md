# Testing baseline (Godot 4)

Testing starts with the **first implemented module**, not with speculative starter-pack scaffolding.

- Pick **GUT or GdUnit4**, compatible with the pinned Godot 4.x minor version, once in `docs/PROJECT_BRIEF.md`.
- A **module** is an implemented component with one responsibility (usually `src/<module>/`). Give its essential logic headless automated tests where feasible.
- An **important interaction** is a contract between two or more modules that affects gameplay/state. Add automated integration tests for those contracts, updating them when either side changes.
- Visual, animation, audio and control **feel** also require a short, relevant **manual checklist**, since headless tests cannot establish quality of presentation.
- Document exact commands to run logic tests headlessly, and keep tests practical. Do not claim tests passed if Godot, the runner or dependencies are unavailable; state **not run and why**.
- Asset resolver tests must cover override precedence, missing/invalid fallback, supported formats and override-root selection, using an injected temporary folder (see `assets/README.md`). Exported-game verification follows guideline 4; if no export was approved, report it as pending.

## Test tiers (M014)

`tools/test.sh` runs the suite in tiers. Each script runs in its own Godot process with its own `user://` folder (`XDG_DATA_HOME`), the heaviest first by the last run's times on this machine (`.godot/test_timings.txt`, a cache; a script never timed counts as slow), four at a time (`-j N` to change, at most the CPU count). After the run it checks that **every script it was given ran and reported** - a script GUT skipped because it failed to parse counts as a failure (`FAILED ... scripts 0`), and so does a crashed process - and fails on any failing test. `-k` keeps the per-script logs.

| Command | What | When | Time here (4 CPUs) |
| --- | --- | --- | --- |
| `tools/test.sh only <name>...` | the scripts whose file names contain any of the names | while changing one module: its unit test and the scene tests that use it | seconds |
| `tools/test.sh unit` | every unit test (the pure models, no scene) | after any change to a pure model | ~70 s |
| `tools/test.sh golden` | the golden master (below) | after any change to how the game runs, before committing | ~35 s |
| `tools/test.sh playthrough` | the eleven multi-night playthroughs (M003-M015) | before committing a stage | ~30 s |
| `tools/test.sh integration` | every scene test | before committing a stage | ~3 min |
| `tools/test.sh full` | everything | before committing; the definition of "the tests pass" | ~4 min |
| `tools/test.sh serial` | everything in one process, as before M014 | at the end of a milestone (it also catches tests that depend on each other's leftovers, which the separate processes hide) | ~13 min |

- **Golden master (M014):** `test_golden_master.gd` drives eight courses of play through the real scene (a new game, the opening skipped, two nights of business and talk with a save and load, Freight Doesn't Walk to the fee, a car saved at the wheel and driven back over a border, the wheel, the machines and the card table, the cafe's film played and the Bird's skipped) and the ten real saves in `tests/fixtures/saves/`, each to a snapshot of the game's state, and compares them with `tests/golden/m013/` - recorded on the M013 code (`29835b7`) before M014 and reproduced by every M014 build. Every generator the game randomizes in play is seeded in the test. **A difference is a change in the game**: investigate it; never re-record to make a test pass. Re-recording (`GOLDEN_RECORD=1`, see the script's header) is only for a milestone that changes the game on purpose, on its reference build, and says so in its report. One recording was taken again in M014, on the M013 reference build (`796d19a`): the one-process run showed that the very first scene in a Godot process gets one frame of the night clock less than any later scene (the M013 code alike), so `new_game` now starts from a scene built in the test, like the other cases, and `new_game.json` holds what M013 gives from that start (the same alone and after other scripts).
- **The physical city (M014):** `test_layout_fingerprint.gd` compares every district layout and room plan, field by field, with `tests/golden/m013/layouts.json` - moving or re-describing the city's data must leave the city where it is.
- **Saves (M014):** `tests/fixtures/saves/m003.json` ... `m013.json` are real saves, each written by that milestone's own code (built from its commit in a git worktree, a little of a night played, saved). `test_save_schema` (pure: versions, migrations, checks) and `test_save_round_trip` (in the game: each loads, is written back at the current format, and loads to the same game) use them; `test_golden_master` compares loading them with how the M013 build loaded them.
- **Architecture (M014):** `test_architecture_wiring` (Dialogue's effects and end hooks, Missions' order and refusals, main making the directors through `Game.make`), `test_game_parts` (every shared part built once, one Game a scene), `test_scene_cleanup` (a freed scene lets its whole game go), `test_modals` (what has the keys; what each screen gives back), `test_district_lifecycle` (a district built, let go and built again), `test_city_locations` (stable ids, local and world coordinates), `test_job_payouts` (each job pays once, also across a save).
